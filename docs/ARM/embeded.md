# 嵌入式底层功底：从编译链接到内存布局，一次讲透

> 很多做嵌入式开发的工程师，平时写代码、编译、下载、调试，整个流程跑得很熟练。但如果问一句：你的 `.c` 文件到底经历了什么，才变成了 MCU Flash 里可以执行的二进制指令？程序里的全局变量、局部变量、常量，在内存中到底是怎么排列的？
>
> 这不是刁钻的面试题，而是嵌入式开发中非常基本的底层认知。

---

## 一、编译链接四部曲：从 .c 到可执行文件

一个 `.c` 源文件，变成最终烧录进 MCU 的固件，要经过 **四个阶段**：

```
.c 源文件  →  预处理  →  编译  →  汇编  →  链接  →  可执行文件
              (.i)      (.s)   (.o)      (.elf/.bin)
```

很多人以为点了 "Build" 就是一步到位，其实编译器（arm-none-eabi-gcc）在背后替你走完了这四步。

### 1.1 预处理：代码的"文本加工"

预处理阶段做的事情**纯粹是文本替换**，不涉及任何语法分析。主要工作包括：

- **宏展开**：把 `#define` 定义的宏替换为实际内容
- **头文件展开**：把 `#include` 引用的文件内容原封不动地插入当前位置
- **条件编译**：根据 `#if`、`#ifdef` 等指令决定保留或删除代码段
- **删除注释**：所有注释在这一步被清除

**示例源码：**

```c
#define BUFFER_SIZE  256

#include "uart.h"

#ifdef USE_DMA
    void send_data(uint8_t *buf, uint16_t len);
#endif
```

经过预处理后：

- `BUFFER_SIZE` 被替换成 `256`
- `uart.h` 的全部内容展开到这里
- `#ifdef` 块根据 `USE_DMA` 是否定义来决定保留还是丢弃

> **小贴士**：用 `-E` 参数可以查看预处理结果
>
> ```bash
> arm-none-eabi-gcc -E main.c -o main.i
> ```
>
> 打开 `.i` 文件，你可能会发现它有几千行甚至上万行 —— 所有头文件都被展开了。

### 1.2 编译：从 C 到汇编

编译器将预处理后的 C 代码翻译成**汇编语言**。这一步会进行：

- **语法分析和语义分析**：检查代码有没有语法错误
- **优化**：根据优化等级（-O0、-O1、-O2、-Os 等）优化代码
- **生成汇编代码**：输出对应目标平台的汇编指令

```bash
arm-none-eabi-gcc -S main.c -o main.s
```

**示例 C 函数：**

```c
int add(int a, int b) {
    return a + b;
}
```

**生成的 ARM 汇编（简化）：**

```asm
add:
    ADD  r0, r0, r1
    BX   lr
```

> ⚠️ **注意**：不同的优化等级会产生完全不同的汇编输出。在 `-O0` 下能正常跑的代码，换到 `-O2` 就出问题，往往根源在于你的 C 代码本身有**未定义行为**，只是在低优化等级下碰巧没暴露而已。

### 1.3 汇编：从汇编到机器码

汇编器将汇编语言翻译成机器可以执行的**二进制指令**，输出目标文件 `.o`。

```bash
arm-none-eabi-gcc -c main.c -o main.o
```

目标文件已经包含了机器码，但**还不能直接运行**。为什么？

因为此时文件里的函数调用和全局变量引用还没有确定最终地址。比如 `main.o` 里调用了 `uart_send()` 函数，但 `uart_send()` 的实现在 `uart.o` 里，`main.o` 此刻并不知道它最终会被放在内存的哪个位置。

这些"待定地址"就是后面链接器要解决的事情。

### 1.4 链接：拼图的最后一步

链接器是整个编译链中**最关键的一环**。它负责把所有的 `.o` 文件、静态库（`.a`）整合在一起，生成最终的可执行文件。链接器的核心工作有三件事：

#### ① 符号解析（Symbol Resolution）

每个 `.o` 文件里都有一张**符号表**，记录了"我定义了哪些符号"和"我引用了哪些外部符号"。链接器负责把所有的符号引用匹配到对应的定义上。

如果某个符号找不到定义，你就会看到经典报错：

```
undefined reference to `uart_send`
```

#### ② 段合并（Section Merging）

每个 `.o` 文件里都有自己的 `.text`（代码段）、`.data`（数据段）、`.bss`（未初始化数据段）等。链接器将所有 `.o` 文件中同名的段合并在一起：

```
file1.o  ─┐
          │  .text ──┐
file2.o  ─┘          ├──→ 合并后的 .text 段
file3.o  ──── .text ──┘
```

#### ③ 重定位（Relocation）

段合并之后，每个函数、每个变量都有了确定的地址。链接器回头把之前那些"待定地址"全部填上正确的值。这个过程就叫**重定位**。

## 二、目标文件里装了什么

编译器生成的 `.o` 目标文件，内部到底是什么结构？

GCC 系列生成的是 **ELF**（Executable and Linkable Format）格式，Keil 的 ARMCC 早期使用 ELF 变体。核心思想是一样的：目标文件由若干个 **段（Section）** 组成。

### 常见段一览

| 段名 | 存储内容 | 运行时位置 | 特点 |
| --- | --- | --- | --- |
| `.text` | 可执行的机器码指令 | Flash | 只读，不可修改 |
| `.rodata` | 只读常量（const 变量、字符串字面量） | Flash | 只读 |
| `.data` | 已初始化的全局变量和静态变量 | RAM（初始值存在 Flash） | 可读写，启动时需从 Flash 搬到 RAM |
| `.bss` | 未初始化或初始化为 0 的全局/静态变量 | RAM | 不占用 Flash 空间，启动时清零 |

### 实际代码示例

```c
const char version[] = "v1.0";       // → .rodata（只读常量）
int system_tick = 0;                  // → .bss（初始化为0，归入BSS）
int error_count = 5;                  // → .data（初始化为非零值）
static int module_state = 3;          // → .data（静态变量，初始化为非零值）

void reset_error(void) {              // → .text（函数代码）
    error_count = 0;
}
```

> 🔍 **容易混淆的点**：`int system_tick = 0;` 虽然写了初始化语句，但因为初始值就是 `0`，编译器通常会把它优化到 `.bss` 段，而不是 `.data` 段。因为 `.bss` 段在固件文件中**不占实际空间**（只需要记录起始地址和长度，启动时统一清零即可），这样可以**减小固件体积**。

### 查看目标文件的段信息

```bash
arm-none-eabi-objdump -h main.o
```

**输出类似：**

```
Sections:
Idx Name          Size      VMA       LMA       File off  Algn
  0 .text         00000024  00000000  00000000  00000034  2**2
  1 .data         00000008  00000000  00000000  00000058  2**2
  2 .bss          00000004  00000000  00000000  00000060  2**2
  3 .rodata       00000005  00000000  00000000  00000060  2**0
```

注意看 **VMA 列全是 0**，这说明目标文件中的段还没有被分配最终地址，要等链接器来分配。

## 三、内存段布局：你的代码和数据住在哪里

嵌入式系统（以 Cortex-M 系列 MCU 为例）的存储器主要分两块：**Flash（非易失性存储）** 和 **RAM（易失性存储）**。

### 整体分布图

```
┌─────────────────────────────────────────────────────────┐
│                        Flash                            │
├──────────┬──────────┬──────────┬────────────────────────┤
│ .isr_    │  .text   │ .rodata  │  .data 初始值副本      │
│ vector   │  代码段  │ 只读常量 │                        │
│ 中断向量 │          │          │                        │
└──────────┴──────────┴──────────┴────────────────────────┘
                                                    ↓ 启动时搬运
┌─────────────────────────────────────────────────────────┐
│                          RAM                            │
├──────────┬──────────────────┬──────────┬───────────────┤
│  .data   │       .bss       │  Heap    │    Stack      │
│          │   未初始化数据   │  ↓↑ 增长 │    ↑↓ 增长     │
└──────────┴──────────────────┴──────────┴───────────────┘
```

下面逐个讲清楚。

### 3.1 .text 段：代码的栖身之所

`.text` 段存放所有编译后的机器码指令，位于 **Flash** 中。CPU 执行程序时，就是从 Flash 的 `.text` 段逐条取指令来运行的。

**两个重要特性：**

- **只读**：Flash 在正常运行时不可被程序改写
- **按函数排列**：每个函数的机器码在 `.text` 段中占据连续的空间，链接器决定它们的排列顺序

### 3.2 .rodata 段：常量的家

`.rodata`（read-only data）段存放只读数据，同样位于 **Flash** 中。典型内容包括：

```c
const uint32_t crc_table[] = { 0x00000000, 0x04C11DB7, ... };
const char *msg = "System Ready";
```

> ⚠️ **容易踩的坑**：如果你忘了加 `const`，一个本该放在 Flash 里的大数组就会被放到 RAM 里（`.data` 段），白白浪费宝贵的 RAM 资源。在资源紧张的 MCU 上，这种疏忽可能直接导致内存不够用。

### 3.3 .data 段：需要"搬家"的数据

`.data` 段是最特殊的一个段，因为它**同时存在于 Flash 和 RAM 两个地方**。

**为什么？看这个变量：**

```c
int error_count = 5;
```

- 初始值是 `5`，这个值**掉电后不能丢**，所以必须存在 Flash 里
- 但运行时程序要修改它的值（比如 `error_count++`），Flash 是只读的
- 所以它又必须住在 RAM 里

**解决方案**：Flash 里存一份"初始值副本"，MCU 上电启动时，由启动代码把这些初始值从 Flash 搬运到 RAM 中对应的位置。

这就是为什么你在链接脚本中经常看到 `.data` 段有**两个地址**：

- **LMA（Load Memory Address）**：加载地址，即数据存储在 Flash 中的位置
- **VMA（Virtual Memory Address）**：运行地址，即数据运行时在 RAM 中的位置

```
Flash:  ┌──────────────┐  LMA = 0x08001000
        │ .data 初始值 │
        └──────────────┘
                ↓ 启动代码搬运
RAM:    ┌──────────────┐  VMA = 0x20000000
        │   .data      │
        └──────────────┘
```

### 3.4 .bss 段：最"经济"的段

`.bss`（Block Started by Symbol）段存放**未初始化或显式初始化为 0** 的全局变量和静态变量。

```c
static uint8_t rx_buffer[1024];   // → .bss
int sensor_value;                  // → .bss
int counter = 0;                   // → .bss（编译器优化）
```

**最重要的特点**：`.bss` 段在固件文件中**不占任何实际空间**。固件里只记录了 `.bss` 段的起始地址和大小，启动时由启动代码将这块区域统一填充为 0。

> 这就是为什么有时候你看到编译输出中 **Flash 占用不大，但 RAM 占用很大** —— 可能就是某个大数组被分配到了 `.bss` 段，不占 Flash 但占 RAM。

### 3.5 Stack 和 Heap

栈和堆**不属于编译器分配的"段"**，而是在链接阶段由**链接脚本预留**的空间。

**栈（Stack）**

- 用于存放局部变量、函数调用的返回地址和寄存器保存值
- 从**高地址向低地址**增长
- 大小在链接脚本中指定
- 嵌入式系统中常见栈大小从几百字节到几 KB 不等
- 如果用了 RTOS，每个任务有自己独立的栈

**堆（Heap）**

- 用于动态内存分配（malloc / free）
- 从**低地址向高地址**增长
- 资源受限的嵌入式系统中，很多团队选择**完全不用堆**，或者使用**内存池**来替代，以避免堆碎片化问题

**两者关系：**

```
高地址  ────────────────────
        │      Stack         │  ← 向低地址增长
        │         ↓          │
        ├────────────────────┤
        │                    │
        │      (空闲区域)    │
        │                    │
        ├────────────────────┤
        │         ↑          │
        │      Heap          │  ← 向高地址增长
低地址  ────────────────────
```

> ⚠️ 如果函数调用层数太深、局部数组太大，栈就可能越过边界踩到堆或者 `.bss` 区域的数据，这就是所谓的 **"栈溢出"**。这种溢出在嵌入式系统中通常没有硬件保护（除非你配置了 MPU），程序可能不会立刻崩溃，而是出现各种诡异的间歇性故障，排查起来极其痛苦。

## 四、链接脚本：内存分区的"规划图"

前面讲了各个段是什么、放在哪里，但有一个关键问题还没回答：**谁来决定这些段放在内存的具体什么位置？**

答案是 **链接脚本（Linker Script）** —— 通常是 `.ld` 文件，Keil 中对应 `.sct` scatter 文件。

链接脚本本质上就是一份**"内存规划图"**，它告诉链接器两件事：

1. 这颗 MCU 有哪些内存区域，各自起始地址和大小是多少
2. 编译出来的各个段应该放到哪个内存区域中去

### 4.1 MEMORY 命令：声明物理内存

以一颗拥有 **512KB Flash、128KB RAM** 的 STM32 为例：

```ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}
```

- `FLASH (rx)` 表示 Flash 区域具有**读（r）** 和**执行（x）** 权限
- `RAM (rwx)` 表示 RAM 具有**读、写、执行**权限
- `ORIGIN` 是起始地址，`LENGTH` 是大小

> ⚠️ 这些地址不是随便写的，必须和芯片数据手册中的**存储器映射完全一致**。

### 4.2 SECTIONS 命令：安排段的位置

有了内存区域定义之后，接下来就是告诉链接器每个段应该放在哪里：

```ld
SECTIONS
{
    /* 中断向量表，放在 Flash 最开头 */
    .isr_vector :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))
        . = ALIGN(4);
    } > FLASH

    /* 代码段 */
    .text :
    {
        . = ALIGN(4);
        *(.text)
        *(.text*)
        . = ALIGN(4);
        _etext = .;         /* 记录代码段结束地址 */
    } > FLASH

    /* 只读数据段 */
    .rodata :
    {
        . = ALIGN(4);
        *(.rodata)
        *(.rodata*)
        . = ALIGN(4);
    } > FLASH

    /* 已初始化数据段：运行在 RAM，加载自 Flash */
    _sidata = LOADADDR(.data);
    .data :
    {
        . = ALIGN(4);
        _sdata = .;          /* .data 段在 RAM 中的起始地址 */
        *(.data)
        *(.data*)
        . = ALIGN(4);
        _edata = .;          /* .data 段在 RAM 中的结束地址 */
    } > RAM AT> FLASH

    /* 未初始化数据段 */
    .bss :
    {
        . = ALIGN(4);
        _sbss = .;           /* .bss 段起始地址 */
        *(.bss)
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;           /* .bss 段结束地址 */
    } > RAM
}
```

**重点看 `.data` 段的这行：**

```ld
} > RAM AT> FLASH
```

- `> RAM` 表示运行时地址（VMA）在 RAM 中
- `AT> FLASH` 表示加载地址（LMA）在 Flash 中
- 这一行就是前面讲的"`.data` 段同时存在于两个地方"的根源

链接脚本中还导出了几个关键符号：`_sidata`、`_sdata`、`_edata`、`_sbss`、`_ebss`。这些符号会被启动代码引用，用来完成数据搬运和 BSS 清零的工作。

### 4.3 链接脚本的重要性

很多嵌入式工程师从来不看链接脚本，觉得这是 IDE 自动生成的东西不用管。大多数时候确实不用改，但一旦你需要做这些事情，就必须读懂它：

- 把某个函数或数据放到指定的内存区域（比如放到 CCM RAM 或 ITCM 中提升性能）
- 在 Flash 中划出一块区域专门存放用户配置数据
- 实现 Bootloader + App 的双区固件方案
- 排查程序运行时内存不足的问题

链接脚本不难，但你得知道它在那里、它在干什么。

## 五、启动代码：串联编译链接与内存布局的关键一环

到这里，编译链接的过程讲完了，内存段布局也讲清楚了。但还差一个关键环节：**程序上电后，谁来完成 `.data` 段的搬运和 `.bss` 段的清零？**

答案是 **启动代码（Startup Code）**，通常是 `startup_xxx.s` 这个汇编文件中的 `Reset_Handler` 函数。

### MCU 启动流程

```
上电复位
   ↓
CPU 从向量表获取 Reset_Handler 地址
   ↓
跳转执行 Reset_Handler
   ↓
┌──────────────────────────┐
│  步骤1：搬运 .data       │  从 Flash 复制初始值到 RAM
│  步骤2：清零 .bss        │  将 BSS 区域全部清零
│  步骤3：系统初始化       │  SystemInit() 时钟配置等
│  步骤4：跳转到 main()    │  开始执行用户代码
└──────────────────────────┘
```

### 启动代码核心逻辑

```c
void Reset_Handler(void)
{
    uint32_t *src, *dst;

    /* 步骤1：将 .data 段的初始值从 Flash 搬运到 RAM */
    src = &_sidata;     // Flash 中 .data 副本的起始地址
    dst = &_sdata;      // RAM 中 .data 段的起始地址
    while (dst < &_edata) {
        *dst++ = *src++;
    }

    /* 步骤2：将 .bss 段清零 */
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }

    /* 步骤3：系统初始化（时钟配置等） */
    SystemInit();

    /* 步骤4：跳转到 main 函数 */
    main();
}
```

`_sidata`、`_sdata`、`_edata`、`_sbss`、`_ebss` 这几个符号，正是链接脚本中导出的那些地址。

**完整链路：**

```
链接脚本定义内存分区和段地址
        ↓
链接器按规则排布各段并导出地址符号
        ↓
启动代码利用这些符号完成内存初始化
        ↓
main() 拿到的是一个已经准备好的运行环境
```

这就是为什么全局变量 `int a = 10;` 在 `main()` 里能直接读到 `10`，为什么未初始化的全局变量默认是 `0` —— 不是编译器自动完成的，是**启动代码在背后干了这些活**。

## 六、实战：查看你的程序到底占了多少内存

理论讲了一大堆，怎么验证？最直接的方式就是看编译输出。

### 6.1 用 size 命令查看段大小

```bash
arm-none-eabi-size firmware.elf
```

**输出：**

```
   text    data     bss     dec     hex  filename
  15248     120    4096   19464    4bf8  firmware.elf
```

**各列含义：**

| 列 | 含义 | 对应的存储器 |
| --- | --- | --- |
| `text` | 代码段 + 只读数据段（.text + .rodata） | Flash |
| `data` | 已初始化数据段（.data） | Flash + RAM（两处都占） |
| `bss` | 未初始化数据段（.bss） | RAM |

**实际占用计算：**

```
Flash 占用 = text + data = 15248 + 120 = 15368 字节
RAM 占用   = data + bss  = 120   + 4096 = 4216 字节
```

> ⚠️ `data` 被算了两次，因为它在 Flash 和 RAM 中各占一份。

### 6.2 MAP 文件：最详细的内存地图

如果你需要更详细的信息（某个函数占了多少字节、某个变量被分配到了什么地址），就要看 **MAP 文件**。

```bash
gcc -Wl,-Map=output.map ...    # GCC 编译时指定
```

Keil 中默认生成 `.map` 文件。

**MAP 文件中的关键信息包括：**

- 每个符号的最终地址和大小
- 每个 `.o` 文件对各段的贡献
- 内存区域的使用率

当你发现 Flash 或 RAM 快用完时，MAP 文件能帮你**精确定位**是哪个模块、哪个变量、哪个函数在"吃"空间。

## 七、写在最后

回过头来看，编译链接和内存布局并不是什么高深的知识，但它是嵌入式开发的**底层地基**。

预处理、编译、汇编、链接四个阶段，每一步都有明确的输入和输出。`.text`、`.rodata`、`.data`、`.bss` 这几个段，各自有各自的规矩：什么数据放在哪里、运行时住在 Flash 还是 RAM、谁来初始化，都是确定的。

- **链接脚本**是这一切的**调度中心**
- **启动代码**是让这一切真正生效的**执行者**

把这条线搞清楚了，你再去看链接脚本就不会觉得像天书，看 MAP 文件就能快速定位内存问题，遇到 HardFault 也不会只能盯着屏幕干瞪眼。

> **嵌入式开发，越往深处走，越需要这些底层功底来撑着。不急，一个一个攻克就好。**
